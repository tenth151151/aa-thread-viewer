# Domain Docs

コードベースを調べるとき、エンジニアリングのスキルがこのリポジトリのドメインの資料をどう読むかを定めます。

## 調べる前に読むもの

- リポジトリの root の **`GLOSSARY.md`**。または、
- root に **`GLOSSARY-MAP.md`** があれば、それ。コンテキストごとの `GLOSSARY.md` を指します。話題に関係するものを、すべて読みます。
- **`docs/adr/`**: これから作業する領域に関わる ADR を読みます。マルチコンテキストのリポジトリでは、コンテキストごとの決定について、`src/<context>/docs/adr/` も確かめます。

これらのファイルがなければ、**何も言わずに進めます**。ないことを指摘せず、先に作ることも勧めません。用語や決定が実際に決まったときに、`/domain-modeling` スキル (`/grill-with-docs` から呼ばれます) が必要に応じて作ります。

## ファイルの構成

このリポジトリは、シングルコンテキストです。

```
/
├── GLOSSARY.md
├── docs/adr/
│   ├── NNNN-<題名>.md
│   └── NNNN-<題名>.md
└── app/src/main/kotlin/
```

マルチコンテキストのリポジトリ (root に `GLOSSARY-MAP.md` がある場合) の構成は、次のとおりです。このリポジトリでは使いません。

```
/
├── GLOSSARY-MAP.md
├── docs/adr/                          ← システム全体の決定
└── src/
    ├── ordering/
    │   ├── GLOSSARY.md
    │   └── docs/adr/                  ← コンテキストごとの決定
    └── billing/
        ├── GLOSSARY.md
        └── docs/adr/
```

## 用語集の語彙を使う

出力でドメインの概念を指すとき (Issue のタイトル、リファクタリングの提案、仮説、テスト名など) は、`GLOSSARY.md` で定義した用語を使います。用語集が避けると明記した同義語に、ずらしません。

必要な概念が用語集にまだなければ、それは合図です。プロジェクトで使わない言葉を作っているか (見直します)、本当に抜けがあるか (`/domain-modeling` に伝えます) のどちらかです。

## ADR との衝突を知らせる

出力が既存の ADR と食い違うときは、黙って上書きせず、はっきり知らせます。

> _ADR-<番号> (<題名>) と食い違いますが、見直す価値があります。理由は…_
