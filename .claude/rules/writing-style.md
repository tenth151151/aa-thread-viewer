# 文体のルール

リポジトリに書く日本語の文体を統一します。コード、コメント、コンソール出力、ドキュメントを書くとき、変更するときに必ず従います。

## 文体と句点

| 対象 | 文体 | 句点 |
|---|---|---|
| コンソール出力 (ログ、エラーメッセージ)、ドキュメント (README、`.md`。`CLAUDE.md` と一部のスキルは例外。下の「常体で書くドキュメント」を参照) | です・ます調 | 文末に付ける |
| コードコメント (シェル、Dockerfile、JSON などすべて) | 常体 (する・である調、体言止めも可) | 文末に付ける |
| コミットメッセージ | 件名は既存の履歴に合わせて「〜した」調 (本文と Dependabot の例外は、下の「コミットメッセージの本文」と「コミットメッセージの例外」を参照) | 付けない |

```bash
# 標準入力が端末のときだけ -t を付ける。
log "Claude Code をインストールします。"
```

### コミットメッセージの本文

本文は、件名との間に空行を 1 つ置き、変えたことごとに 1 行ずつ書きます。何を変えたかと、その意図を書きます。文末は「〜した」調でなくてもかまいません (例: 「…末尾の空白だけの行をすべて捨てる」)。句点は付けません。

コミットメッセージの件名と本文には、下の「Issue や PR ではない番号に `#` を付けない」の節も当てはまります。

### コミットメッセージの例外

Dependabot が作るコミットは、英語の既定のメッセージ (`Bump ...`) のままにします。それ以外のコミットは、件名を「〜した」調で書きます。本文は、上の「コミットメッセージの本文」に従います。

### 常体で書くドキュメント

次のファイルは、常体 (する・である調) で書きます。例外の一覧は、この節を正とします。

- `CLAUDE.md`
- `.claude/skills/squash-commits/SKILL.md`

理由は、既存の書き方を踏襲するためです。

ルール (`.claude/rules/`)、エージェント (`.claude/agents/`)、`tdd` と `pre-pr-check` の `SKILL.md`、`README.md` は、です・ます調で書きます。新しいスキルも、です・ます調で書きます。常体で書くときは、この節の一覧に足します。

### 句点の例外

- 見出しのコメントには付けません。`# ---` で囲んだセクション見出しのタイトル行と、後ろに説明の行 (`#   ...` や `# * ...`) が続くタイトル行の、どちらも対象です。説明の行は、通常のコメントとして句点を付けます。
- 文末が `！` `？` の文には、句点を重ねません。
- コマンド名、パス、URL、バージョンなどの値で終わる行は、句点を付けると誤読されやすいので付けません。
- 文の途中で改行したコメントは、最後の行にだけ句点を付けます。
- 括弧書きだけで 1 文になるときは、括弧の中に句点を入れます (例: `# (理由はこれである。)`)。

## 書式

- 句読点は全角の `、` `。` を使います。
- 日本語と英数字の間には、半角スペースを入れます (例: `sudo を削除します。`)。
- 丸括弧は半角の `(` `)` を使います。全角の丸括弧 (U+FF08、U+FF09) は使いません。
  - 半角の丸括弧と、日本語、英数字、インラインコードの間には、括弧の外側に半角スペースを入れます (例: `常体 (する・である調) で書きます。`)。括弧の内側にはスペースを入れません。
  - 次の場所には、スペースを入れません。
    - 句読点 (`、` `。`) の前後と、`:` の前。
    - 行頭と行末。
    - ほかの括弧類 (`「` `」` `[` `]` `(` `)` など) の隣。
  - コードの中の括弧 (関数呼び出しなど) には、この決まりを当てはめません。
  - 全角の丸括弧があるかどうかは、`bin/check-fullwidth-parens.sh` で調べます。CI と Claude Code のフック (`.claude/settings.json`) で自動で動きます。スペースの付け方は検査しません。
  - フックは 2 つあります。どちらも、見つけたときと、git が失敗して検査できなかったときは、終了コード 2 で Claude に知らせます (見つけたときは場所も出します)。ただし、ツールはもう実行したあとなので、書き込みは止まりません。
    - Write、Edit、MultiEdit、NotebookEdit のあとに動くフックは、編集したファイルだけを検査します。ファイルは、それが属する git のリポジトリ (別の git worktree を含む) の中で検査します。git のリポジトリに属さないファイルは検査しません。編集したファイルのパスを取り出せないとき (`jq` がないときなど) は、リポジトリ全体を検査します。
    - Bash のあとに動くフックは、`bin/check-fullwidth-parens-changed.sh` で、作業ツリーで変わったファイル (HEAD との差分と未追跡のファイル。削除したファイルは除く) を、`bin/check-fullwidth-parens.sh` に一度に渡して検査します。フックの入力の `cwd` (`jq` がないときはカレントディレクトリ) が属する git のリポジトリを調べ、リポジトリの外では何もしません。変わったファイルがなければすぐ終わります。
  - Bash のあとのフックでは、次の場合に見つかりません。
    - 書き換えたファイルを、同じコマンドの中でコミットしたとき。HEAD との差分に残らないためです。コミットされたファイルは、CI で見つかります。
    - `.gitignore` されたファイルを書き換えたとき。`bin/check-fullwidth-parens.sh` がもともと対象外にしていて、CI も同じスクリプトを使うので、CI でも見つかりません。
    - 別のリポジトリのファイルを、絶対パスで書き換えたとき。このリポジトリの検査の対象外なので、このリポジトリの CI でも見つかりません。
  - もとから全角の丸括弧を含む変更が作業ツリーにあると、Bash を呼ぶたびに、直すまで同じ指摘が出ます。直すべきものなので、受け入れます。
  - アプリの画面に出す文字列 (`app/src/*/res/`) と、テストのデータ (`app/src/*/resources/`) は、AA を含むことがあるので、検査の対象外です。AA を含む文字列は、Kotlin のコードに直接書かず、これらのファイルに置きます。画面の文章の書き方は、別に決めます。
- 省略記号は `…` を使うか、使わずに書きます (`...` は使いません)。
- 複数の文を書くときも、各文を句点で区切ります。

## 経緯と参照を書かない

コード、コメント、コンソール出力、ドキュメント (ルール、スキル、エージェントを含む) には、今の決まりと、その理由、確かめた事実だけを書きます (この節で禁止の例として挙げる書き方は除きます)。

- Issue や PR への参照 (番号やリンク。`#27`、`Issue #10` など) を書きません。読む人がその場で意味を取れず、内容が古くなっても気づきにくいためです。
- 変更の経緯 (いつ、どの Issue や PR で入れたか、以前はどうだったか) を書きません。経緯は、コミットメッセージと PR の本文に書きます。
- 確かめた事実がいつの時点のものかを示すときは、日付ではなく、確かめた版 (ライブラリやツールのバージョン) で示します。確かめ直す目安になるためです。
- 確かめた事実には、ユーザーが手で確かめて、Issue や会話に書いたことも含みます。
  - 書くのは、観察した範囲までです。観察からの推論は、事実として書きません。
  - 書かないのは、Issue の番号と、どの Issue や会話で確かめたかです。確かめ方 (例: 使い捨てのプロジェクトでの検証) は、書いてかまいません。確かめた版が分かるときは、版で示します。
  - ユーザーが確かめたことを、「確かめていません」と弱めて書きません。確かめた事実が伝わらないためです。
- 「今は」「まだ」などで今の状態を説明すること (例: 今の画面には ViewModel がない) は、経緯ではないので、書いてかまいません。
- コミットメッセージ、PR の本文、Issue の本文は、この決まりの対象外です。
- `.out-of-scope/` のファイルの `## Prior requests` の節も、対象外です。同じ要望の記録で、Issue トラッカーの記録に近いためです。
- `docs/adr/` の ADR の、検討した案と、Status の置き換わった先 (`superseded by ADR-<番号>`) も、対象外です。ADR は、決定の理由と置き換わりの記録であるためです。

## Issue や PR ではない番号に `#` を付けない

GitHub に書く文章 (Issue と PR のタイトル、本文、コメント、レビューのコメントと、コミットメッセージの件名と本文) では、Issue や PR ではない番号 (Dependabot alert、Code scanning alert、Security Advisory など) を `#<番号>` の形 (例: `Dependabot alert #10`) で書きません。URL (例: `https://github.com/<owner>/<repo>/security/dependabot/<番号>`) か、`GHSA-…` などの ID で書きます。GitHub は、これらの文章の `#<番号>` を同じリポジトリの Issue か PR へのリンクにし、指された Issue や PR に参照の記録を付けるため、関係のない Issue や PR に記録が付くからです。

コミットメッセージ、PR の本文、Issue の本文は、上の「経緯と参照を書かない」の対象外ですが、この決まりは当てはまります。

## 口調の設定をファイルに持ち込まない

チャットでの返答に使う口調やキャラクターの設定 (語尾など) を、コード、コメント、コンソール出力、ドキュメント、コミットメッセージに書いてはいけません。ファイルに書く文章は、上の表のとおりに書きます。
