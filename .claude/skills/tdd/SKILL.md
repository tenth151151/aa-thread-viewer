# TDD の 1 サイクルを回す

原則と役割分担は `.claude/rules/tdd.md` に従います。このスキルは、その原則をこのプロジェクトで実行するためのコマンドと確認方法をまとめたものです。ルールの例外に当たる変更（ドキュメント、設定ファイルなど）は、ルールに従い、このスキルを使いません。

## 前提

- モジュールは `:app` の 1 つです。パッケージは `io.github.tenth151151.aathreadviewer` の下に置きます。
- 本体は `app/src/main/kotlin/<パッケージのパス>/`、テストは `app/src/test/kotlin/<パッケージのパス>/` に置きます。テストのファイル名は `<対象>Test.kt` とします。
- テストは JUnit 4 のローカル単体テストです。エミュレータは使えない前提なので、計装テスト（`androidTest`）は使わず、ロジックは JVM で試せる単体テストに寄せます。
- テスト名は、振る舞いが分かる日本語の文（バッククォート囲み）にします。

## 実行コマンド

```bash
# すべての単体テストを実行する。
./gradlew :app:testDebugUnitTest --rerun

# 特定のテストに絞る。クラス名、メソッド名のどちらにも、ワイルドカードを使える。
./gradlew :app:testDebugUnitTest --rerun --tests '*DatLineParserTest'
./gradlew :app:testDebugUnitTest --rerun --tests '*DatLineParserTest.*2行目*'

# コンパイルだけを確認する（テスト）。
./gradlew :app:compileDebugUnitTestKotlin
```

- 入力が変わっていないと、タスクが `UP-TO-DATE` になり、テストが実際には走りません。結果を確認するときは、必ず `--rerun` を付けます。
- `--tests` の条件に合うテストが 1 つもないと、`No tests found for given includes` で失敗します。絞り込みの指定が誤っているので、指定を直します。
- 結果は `app/build/test-results/testDebugUnitTest/*.xml` に出ます。先頭の `<testsuite>` 行の `tests`、`failures`、`errors` で、実行数と失敗数を確認します。
- `--tests` で絞って実行した後は、結果の XML も絞った分だけになります。最終確認は、全件（`--tests` なし、`--rerun` 付き）で行います。

```bash
grep -o 'tests="[0-9]*" skipped="[0-9]*" failures="[0-9]*" errors="[0-9]*"' app/build/test-results/testDebugUnitTest/*.xml
```

## 始める前に

1. 今回のサイクルで扱う振る舞いを 1 つに決めます。複数ある場合は、サイクルを分けます。
2. 扱わないこと（後のサイクルに回すこと）を書き出します。例: 「不正な行の扱いは次のサイクル」。
3. 既存のテストと本体を読み、命名や書き方を合わせます。

## 赤

### テストを書く

1. 期待する振る舞いを表すテストを書きます。新しい型や関数を作る場合、本体はまだ作りません。
2. 期待値は、振る舞いがテストから分かる値にします。たとえば、加工しない振る舞いなら、本文の前後の空白を残した値を使います。

### 新しい型や関数を作る場合（2 段階とも必須）

1. 1 段階目: コンパイルエラーを確認します。
   1. `./gradlew :app:compileDebugUnitTestKotlin` を実行し、未定義の型や関数が原因のコンパイルエラーになることを確認します。
2. 2 段階目: 誤った値を返す本体で、期待値の不一致を確認します。
   1. コンパイルが通る最小限の本体を作り、わざと誤った値を返すようにします。
   2. `./gradlew :app:testDebugUnitTest --rerun --tests '<テスト>'` を実行し、期待値と実際の値の不一致（`AssertionError` や `ComparisonFailure`）で失敗することを確認します。

### 既存の本体を変える場合

バグ修正や、既存の関数への振る舞いの追加などが当たります。コンパイルエラーにならないので、1 段階目は行いません。テストを書いて `./gradlew :app:testDebugUnitTest --rerun --tests '<テスト>'` を実行し、期待値の不一致で失敗することを確認します。

### 共通の注意

- `TODO()` の例外で失敗させません。意図した失敗ではなく、テストが正しく書けているか分からないためです。
- 最初から通る場合や、期待と違う理由で失敗する場合は、テストを直します。

## 緑

1. テストを通すための最小限の実装を書きます。先回りして機能を足しません。
2. `./gradlew :app:testDebugUnitTest --rerun`（`--tests` なし）で全テストを実行し、すべて通ることを確認します。結果の XML で、`tests` が期待どおりで、`failures` と `errors` が 0 であることも見ます。

## リファクタリング

1. テストが通ったまま、重複や分かりにくさを整えます。
2. 整えるたびに `./gradlew :app:testDebugUnitTest --rerun`（`--tests` なし）を実行します。
3. 整える対象は、今回のサイクルで書いたコードに限ります。

## 報告に含めること

worker は、次のことを報告します。

- 今回扱った振る舞いと、扱わなかったこと。
- 赤の 1 段階目（新しい型や関数を作った場合）: 実行したコマンドと、コンパイルエラーの抜粋。
- 赤の 2 段階目（新しい型や関数を作った場合）: 実行したコマンドと、期待値の不一致で失敗した抜粋。
- 既存の本体を変えた場合の赤: 実行したコマンドと、期待値の不一致で失敗した抜粋。
- 緑: 実行したコマンドと、`BUILD SUCCESSFUL` および XML の `tests` と `failures` の値。
- リファクタリングをしたときは、その内容と実行結果。
- コミットの前: `./gradlew check assembleDebug` の実行結果（`BUILD SUCCESSFUL` か、失敗の抜粋）。
- 実行できなかった確認があるときは、そう明記します。

## reviewer の確認手順

reviewer は読み取り専用で、実物のファイルを変えません。

1. テストが先に書かれたことは、worker の報告にある赤の各段階のコマンドと出力で確かめます。テストと実装は 1 コミットにまとめるので、履歴からは順序が分かりません。
2. テストが誤った実装を検出できることを確認するため、赤を再現します。再現しても、テストが先に書かれたことの証明にはなりません。
   1. スクラッチパッドにリポジトリをコピーします（`build/` や `.gradle/` は除いてかまいません）。
   2. コピーの側で、本体を誤った値を返す形に置き換えます。
   3. コピーの側で `./gradlew :app:testDebugUnitTest --rerun --tests '<テスト>'` を実行し、期待値の不一致で失敗することを確認します。
3. 実物のリポジトリで `./gradlew :app:testDebugUnitTest --rerun` を実行し、すべて通ることを確認します。
4. テストが振る舞いを正しく表しているかを確認します。次の点を見ます。
   - 期待値が、振る舞いを区別できる値になっているか。
   - 扱わないと決めたことまでテストしていないか。
   - テストが弱められたり、スキップされたりしていないか。

## コミットの前に

作業の最後（コミットや PR の前）に、CI と同じ確認として次を実行します。

```bash
./gradlew check assembleDebug
```

- `check` には、単体テスト、Android Lint（警告もエラー）、`spotlessCheck` が含まれます。
- format の崩れで失敗したときは、`./gradlew spotlessApply` で直し、もう一度実行します。
- 緑とリファクタリングの途中は、これまでどおり `./gradlew :app:testDebugUnitTest --rerun` で確認します。

## コミットの単位

1 サイクル（テストと実装）を 1 コミットにします。worker はコミットしません。コミットは、supervisor の指示で helper が行います。ブランチ内のコミットをまとめるときは、`/squash-commits` に従います。

- 1 サイクルで 1 コミットにすると、各コミットでテストが通る状態になります。
- テストが先だったことは、履歴ではなく worker の報告で確かめます。
