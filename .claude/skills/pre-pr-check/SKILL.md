# PR を作る前の確認

ブランチと `origin/main` の差分を、`/code-review` と `claude doctor` で確認します。差分にコンテナで動かせないファイルがあるときは、手順 1 でユーザーにホストでの確認を頼みます。自明な修正はそのまま直し、確認が必要な指摘はユーザーに見せて、直すものを選んでもらいます。
実行するのは supervisor (監督) です。**確認が必要な指摘は勝手に直しません**。

## 流れの中での位置

worker の作業 → reviewer の確認 → helper のコミット → **`/pre-pr-check`** (最初にホストでの確認) → (指摘を直したら、worker → reviewer → helper のコミット) → `/squash-commits` → push と PR の作成

- **`/squash-commits` より前に行います**。指摘を直したコミットを、`/squash-commits` で元のテーマのコミットにまとめられるためです。まとめたあとに確認すると、直したあとにまとめ直しが必要になります。

## 1. 状態を確認する

```bash
git fetch origin
git fetch origin main:main               # ローカルの main を origin/main まで進める。
git status --short                       # 未コミットの変更が無いこと。
bash bin/check-fullwidth-parens.sh       # 全角の丸括弧が無いこと。
git branch --show-current
git log --oneline origin/main..HEAD      # 確認の対象。
git diff --name-only origin/main...HEAD  # 変更されたファイル。
```

- `git fetch origin` のあとは、すべて `origin/main` と比べます。このリポジトリでは PR を GitHub でマージするので、ローカルの `main` は古いままのことが多いためです。`git fetch origin` で更新した `origin/main` と比べれば、ローカルの `main` の新しさに左右されません。
- `git fetch origin main:main` で、ブランチを切り替えずに、ローカルの `main` を `origin/main` まで進めます。`/code-review` はローカルの `main` と比べることがあり、続けて行う `/squash-commits` もローカルの `main` を基点にするためです。`main` がそろっていれば、どちらと比べても同じ差分になります。
- `git fetch origin main:main` が失敗したとき (ローカルの `main` に `origin/main` にないコミットがある、など) は、先に進まずユーザーに伝えます。
- `git fetch origin` が失敗したときは、`origin/main` が古いまま比べることになるので、先に進まずユーザーに伝えます。
- 未コミットの変更がある場合は、先にコミットするかをユーザーに聞きます。差分に含まれない変更は、確認の対象になりません。
- `bin/check-fullwidth-parens.sh` が 1 で終わった (全角の丸括弧が見つかった) ときは、`/code-review` より先に、見つかった箇所を `.claude/rules/writing-style.md` の決まりで半角に直します。コメント、ドキュメント、Claude への指示のファイルの中なら、文体のルールへの違反の修正なので、自明な修正として扱います。コードの文字列の中は、手順 4 の線引きで仕分けます。確認が必要なものは、ユーザーに聞いてから直します。直すときは手順 5 と同じ流れ (worker → reviewer → helper のコミット) で行い、コミットしたあとにスクリプトをもう一度実行して、0 で終わることを確かめてから手順 2 に進みます。
- `bin/check-fullwidth-parens.sh` が 2 以上で終わったときは、検査そのものが失敗しており、結果が分かりません。問題なしとは扱わず、先に進まずユーザーに伝えます。
- 最後に、差分に、コンテナで動かせないファイルがあるかを判断します。コンテナでは、Windows PowerShell でスクリプトを実行できず、コンテナの作り直しもできないため、確かめずに PR を出すおそれがあるためです。

  ```bash
  git diff --name-only --diff-filter=d origin/main...HEAD | grep -E '^bin/windows/'
  ```

  - `--diff-filter=d` は、消したファイルを除きます。消したファイルは、動かして確かめるものがないためです。
  - `grep` は、当たらないと終了コード 1 になります。これは「対象なし」のふつうの結果で、失敗ではありません。
  - `grep` は `bin/windows/` の下だけに当たります。当たらなくても、それだけで対象外とはせず、差分のファイルの一覧を見て、コンテナで動かせないファイルがないかを判断します。
  - 判断の例は、次のとおりです。
    - `bin/windows/` の下のスクリプト (`setup-emulator.ps1` と `setup-emulator.bat`)。Windows のホストで、Windows PowerShell で動きます。
    - `.devcontainer/` の `Dockerfile`、`devcontainer.json`、`bin/post-create.sh` など。動作を確かめるには、ホストでコンテナを作り直す必要があるので、同じ扱いにします。
  - 該当するファイルがないときは、何もせず、「対象外」として手順 6 で報告します。
  - 該当するファイルがあるときは、`/code-review` より前に、supervisor がユーザーに、ホストでの実行と確認を頼みます。何を実行して、何を見てほしいかを具体的に書きます。
    - 実行するコマンド (リポジトリのフォルダでの実行例を含む)。
    - 出てほしいメッセージや、終了後の状態。
    - かかる時間の目安。
  - 結果 (確かめたこと、確かめられなかったこと) は、手順 6 の報告と、PR の本文の「確かめたこと」に書くために、控えます。
  - ユーザーがすぐに確かめられないときは、PR を作らずに待つか、確かめていないと PR の本文に書いて進めるかを、ユーザーに選んでもらいます。supervisor は勝手に選びません。
  - ホストでの確認で問題が見つかったときは、直し方をユーザーに決めてもらってから直します。挙動が変わるので、手順 4 の「確認が必要」と同じ扱いです。直すときは、worker → reviewer → helper のコミットの流れで行い、もう一度ホストでの確認を頼みます。直したものは、手順 2 の `/code-review` (high) の対象に入ります。

## 2. `/code-review` を実行する

ブランチと `origin/main` の差分 (`origin/main...HEAD`) を対象にします。

- Skill ツールで呼び出します。
  - 例: `skill: code-review`、`args: "high --max-findings all main...HEAD"`
  - 対象を `main...HEAD` で渡すのは、比べる相手をはっきりさせるためです。手順 1 でローカルの `main` を `origin/main` にそろえてあるので、`origin/main` と比べるのと同じになります。
- 実行したときの HEAD (`git rev-parse HEAD`) を、「確認したコミット」として控えます。2 回目以降の範囲の始点に使うためです。
- 1 回目の effort level は `high` に固定します。指定しないと前回の level が使われ、深さが毎回変わるためです。PR を出す前の最後の確認なので、1 回目は `high` にします。2 回目以降は手順 5 のとおり `low` にします。
- `--max-findings` は `all` にします。`default` では high のとき最大 10 件に絞られます。指摘をすべて表にまとめるので、上限をなくします。`--max-findings` は前回の値が引き継がれるので、毎回指定します。
- 対象を照合します。
  - `/code-review` の結果の冒頭には、対象の説明 (例: `git diff main...HEAD`、コミット数、ファイル数) が出ます。この説明が、`git log --oneline origin/main..HEAD` のコミット数と `git diff --name-only origin/main...HEAD` のファイル数と一致することを確かめます。一致しないときは、指摘を使う前にユーザーに伝え、どうするかを決めてもらいます。
  - 説明が出ないときは、「対象を照合できなかった」と報告に書きます。
  - 結果が `(none)` だけのときは、指摘がないという結果として扱い、実行し直しません。対象の説明がないので、「対象を照合できなかった」と報告に書きます。
  - 差分にないファイルへの指摘 (呼び出し元や、関係するほかのファイルへの影響) は、食い違いではありません。普通の指摘として扱います。
- 結果はバックグラウンドで届きます。届くまで待ちます。
- 結果は英語で返ることがあります。ユーザーには日本語で伝えます。

## 3. `claude doctor` を実行する

差分に Claude 関係のファイル (`CLAUDE.md`、`.claude/` 配下、`.mcp.json`) があるときだけ実行します。手順 1 で未コミットの変更がないことを確かめた前提で、`origin/main...HEAD` (コミット済みの差分) を見ます。

```bash
git diff --name-only origin/main...HEAD | grep -E '^(CLAUDE\.md|\.mcp\.json)$|^\.claude/'
```

- 該当するファイルがある場合: supervisor が自分で、リポジトリのルートで `claude doctor < /dev/null` を実行し、出力の全文を見ます。ほかのエージェントを通すと、出力が要約されて「Invalid settings」を見落とすおそれがあるためです。
- 該当するファイルがない場合: 実行せず、「対象外」として報告します。

`claude doctor` の性質は、次のとおりです。

- カレントディレクトリの settings ファイルを読んで検証します。permission のルールの書式の誤りや、値の型の誤りは、「Invalid settings」の節に出ます。
- git に入っていない `.claude/settings.local.json` も検証するので、差分にないファイルの指摘が出ることがあります。そのときは、差分の問題ではないことを分けて報告します。
- 問題があっても終了コードは 0 になります。**出力に「Invalid settings」があるかで判断します**。
- 未知のキーは指摘しません。
- スキルやエージェントの定義、`CLAUDE.md` の中身が検証の対象かどうかは、確かめていません。
- セッションの中の `/doctor` は Claude からは実行できません。必要ならユーザーに頼みます。

## 4. 指摘を表にまとめて、直し方を決める

`/code-review` と `claude doctor` の結果を、次の列の表にまとめます。

| 深刻度 | 場所 | 内容 | おすすめの対応 |
|---|---|---|---|

- `/code-review` は深刻度を出さないので、深刻度 (高、中、低) は supervisor が判断してつけます。判断でつけたことを、表の前に一言書きます。
  - **高**: 壊れるもの、データや設定を失うもの、安全に関わるもの。
  - **中**: このプロジェクトのふだんの流れで起こる失敗の筋書きを、具体的に書けるもの (ルールの矛盾、抜けた分岐、誤った手順など)。まれな場合や、仮の話にとどまる指摘は、低にします。
  - **低**: 動きは変わらないもの (読みやすさ、表記など) と、まれな場合や仮の話にとどまるもの。
  - 深刻度は、手順 5 で `/code-review` を繰り返すかどうかの判断に使います。基準に沿ってつけます。高と中で迷ったときは高にします。中と低で迷ったときは、失敗の筋書きを具体的に書けるかで決め、書けないものは低にします。
- 指摘が無いときは、手順 6 に進みます。
- 「おすすめの対応」の列には、「自明 (そのまま直す)」「確認が必要 (直す)」「確認が必要 (直さない)」のように、自明か確認が必要かが分かるように書きます。
- 自明かどうかは、次の線引きで決めます。この線引きは、reviewer の指摘のうち、依頼した作業の範囲を越えるものにも使います (`.claude/agents/supervisor.md` を参照)。
  - **自明 (そのまま直す)**: コメントとドキュメントの中の、句点、表記ゆれ、言い回し、誤字、文体のルールへの違反。ソースや実行結果で確かめた事実の訂正 (コメントとドキュメントの中だけ)。ただし、Claude への指示のファイル (`CLAUDE.md`、`.claude/` 配下のスキル、エージェント、ルール) は、句点、表記ゆれ、言い回し、誤字、文体のルールへの違反の修正だけが自明です。内容の変更は「確認が必要」です。
  - **確認が必要**: 次のものです。迷ったら、こちらに入れます。
    - 挙動が変わるもの (コード、設定、permission、CI、ビルド、Dockerfile)。コードの中の事実の誤りの訂正も含みます。
    - コードの中のログやメッセージの文言の変更。
    - Claude への指示のファイルの内容の変更。エージェントの動きが変わるためです。
    - 範囲を広げる・狭めるもの (新しい手順や項目を足す、消す)。
    - 複数のやり方があって、選ぶ必要があるもの。
- 自明なものも含めて、すべての指摘を 1 つの表にまとめて、ユーザーに見せます。
- そのうえで、確認が必要な指摘だけを、AskUserQuestion で、どれを直すか選んでもらいます。選択肢は 4 つまでなので、指摘を 1 件ずつ選択肢にしません。「おすすめどおり (Recommended)」「深刻度が中以上だけ」「全部」のように、まとめた選択肢で聞きます。**おすすめどおりの選択肢を先頭に置きます**。個別に変えたいときは、ユーザーが「Other」で書きます。
- 確認が必要な指摘がなければ、表を見せたあと、聞かずに手順 5 に進みます。
- 確認が必要な指摘のうち、選ばれなかったものは直しません。
- 自明な指摘は、確認せずに手順 5 で直します。

## 5. 指摘を直す

- 自明な指摘と、直すと決まった指摘は、worker → reviewer → helper のコミット の流れで直します。自明な修正も、reviewer の確認を通します。
- 直したものをコミットしたあと、`/code-review` をもう一度実行するかを決める前に、直した差分に、コンテナで動かせないファイルがあるかを、手順 1 と同じ判断 (`grep` だけでなく、差分のファイルの一覧を見ます) で確かめます。あるときは、自明な修正だけのときも含め、もう一度ホストでの確認を頼みます (手順 1 と同じ頼み方です)。ないときは頼みません。手順 4 に戻ったあとにまた直したときも、同じように確かめます。
- 手順 5 で頼み直したホストでの確認で問題が見つかったときは、次のとおりにします。
  - その直しは、手順 2 の `/code-review` のあとにあり、下の再実行の条件にも当たらないので、そのままでは `/code-review` を通りません。
  - 直し方は、手順 1 と同じく、ユーザーに決めてもらってから直します。
  - 直した差分に `/code-review` を `low` で 1 回行います。この 1 回は、下の再実行の条件にかかわらず、また 3 回の上限に達していても行います。ユーザーへの確認は要りません。実行した回数には数えるので、回数が 3 回を超えることがあります。呼び出し、「確認したコミット」の扱い、対象の照合、結果の扱い (`(none)` だけのときを含む) は、2 回目以降の `/code-review` と同じです。
  - そのあと、もう一度ホストでの確認を頼みます。
- 直すものがない (自明な指摘がなく、確認が必要な指摘もすべて直さないと決まった) ときは、手順 6 に進みます。自明な修正だけのときは、`/code-review` をもう一度実行せず、手順 6 に進みます。
- `/code-review` をもう一度実行するのは、次の 3 つをすべて満たすときだけです。
  1. 確認が必要な指摘を直したこと。
  2. 直前の `/code-review` の結果に、深刻度が中か高の指摘があったこと。
  3. このブランチで `/code-review` を実行した回数が、まだ 3 回未満であること。
  - 候補は、深刻度をつけず、条件 2 の判断にも入れません。
  - 3 つを満たすときも、もう一度実行するかはユーザーに確認します。
  - 直前の結果が低の指摘だけだったときは、もう実行しません。低の指摘も、手順 4 の表で仕分けて、自明なものは直し、確認が必要なものは聞きます。
  - 3 回目の `/code-review` の結果に中か高の指摘があり、確認が必要な指摘を直したときは、ユーザーに「続ける」「残りを Issue にして進める」のどちらかを選んでもらいます。「続ける」を選んだときは、1 回だけ追加で実行します。そのあとも中か高の指摘が残ったときは、また同じように選んでもらいます。「残りを Issue にして進める」を選んだときは、Issue の文面をユーザーに見せて、作成の確認を取ってから作ります。
- 2 回目以降の `/code-review` は、直した差分だけを対象にします。呼び出しは `args: "low --max-findings all <確認したコミット>..HEAD"` です。
  - 直した差分だけを見るのは、2 回目以降の目的が、前の回の指摘が直ったかと、直したことで新しく壊れたものがないかを確かめることだからです。`low` にするのは、確信の高い指摘だけを出すためです。
  - 実行したあとは、「確認したコミット」を、そのときの HEAD に置き換えます。
  - 対象の照合は手順 2 と同じ考え方で、`git log --oneline <確認したコミット>..HEAD` のコミット数と、`git diff --name-only <確認したコミット>..HEAD` のファイル数で行います。
  - 直した差分と前の回の指摘に関係する指摘は、手順 4 の表にまとめます。それ以外の指摘 (前の回の範囲に関係しない新しい指摘) は、自分の判断では直さず、「候補」として表とは分けてユーザーに見せます。候補をこのブランチで直すか、Issue やメモにするか、何もしないかは、ユーザーが決めます。
- 再実行した `/code-review` の結果が `(none)` だけのときは、関係する指摘がないものとして扱います。対象の説明がないので、「対象を照合できなかった」と報告に書きます。実行した回数に数え、「確認したコミット」も、そのときの HEAD に置き換えます。手順 4 に戻るかは、次の判断のとおり、`claude doctor` の新しい指摘だけで決めます。
- 再実行した `/code-review` に、直した差分や前の回の指摘に関係する指摘があるとき、または `claude doctor` に新しい指摘があるときは、手順 4 に戻ります。候補だけのときは、手順 4 に戻らず、手順 6 に進みます。再実行しないとき、または手順 4 に戻る指摘がないときも、手順 6 に進みます。
- 直した差分に Claude 関係のファイルがあれば、手順 3 の `claude doctor` を supervisor が自分でもう一度実行します。すぐに終わるので、毎回行います。`claude doctor` に新しい指摘があれば、自明な修正だけのときも、手順 4 に戻ります。

## 6. 報告する

- `/code-review` の結果の要約 (日本語) を書きます。
- `/code-review` を実行した回数と、繰り返しを終えた理由 (低の指摘だけになった、3 回に達した、Issue にして進めた、など) を書きます。
- `claude doctor` の結果、または「対象外」であることを書きます。
- 自明として直した指摘と、その直し方を報告します。
- 手順 1 で全角の丸括弧を直したときは、直した箇所とその直し方を報告します。手順 4 の表を通らないため、ここで書かないと報告から漏れます。
- 確認が必要な指摘のうち、直したものと、直さなかったものを書きます。
- 「候補」として見せた指摘があれば、それを書きます。
- 手順 1 のホストでの確認の結果 (ホストで確かめたこと、確かめられなかったこと、または「対象外」) を書きます。PR の本文の「確かめたこと」にも同じ内容を書くことを伝えます。
- 次は `/squash-commits` に進むことを書きます。
